> **何時讀**：核心某條命中、而且你要據以動手（寫入、採用、宣告完成、設計比對或驗收器）時，讀本檔同編號那一節。

## Rubric 1：何時升級模型 / 找第二意見

> 主模型已是 opus 時，「升級」的實體是 **fresh-context 對抗審查**（同級模型 + 不知前情 + 找問題立場），不是換更強的模型；判準與時機不變（見 [01_dispatch.md](../rules/01_dispatch.md) §3 末條）。

**升級訊號（任一命中即升，配合 [01_dispatch.md](../rules/01_dispatch.md) §5）**：
- 問題本質是「取捨」而非「執行」：多個方案各有利弊、或驗收標準本身需要先被定義
- 數字都算對了，但「該不該採用」拿不準（統計顯著 vs 過擬合、增益來源乾不乾淨）
- 同一子任務失敗 2 次，且兩次失敗原因**不同**（原因相同是執行問題，修就好；原因不同代表理解錯了）

**正例**：v351 的門檻掃描結果單調遞增，機械上看該採用最緊值；但增益全來自 2020 崩盤的深空贏單——「sweep 單調 ≠ 可採用，必須時間均勻」是品味判斷，這種問題該派 fresh-context 第二意見而不是自己拍板（project_v351_baseline）。
**反例（不該升級）**：把已驗證的 give-back 條件複製到另一個訊號並跑回測——純執行，sonnet 足夠；升級只是變慢變貴。

## Rubric 2：何時算「真的完成」

完成 = **驗收證據在手**，不是「我改完了」：
- 程式碼：測試綠（且通過下方「綠燈／零錯誤計數本身也要被驗」）/ 實跑輸出貼在回報裡。回測改動：六訊號全跑完 + sanity（未動的訊號結果 bit-identical）
- 檔案/文件：fresh agent read-back 通過（[01_dispatch.md](../rules/01_dispatch.md) §6）
- 修 bug：能說出**根因**並解釋舊行為為何發生。「改了之後不再出現」不算——可能只是壓住症狀
- 涉及排程/服務（.bat、NSSM、cron）：實際觸發一次或查到下次排程時間，不能只看檔案內容對；常駐服務的看門狗另依 [06_service_safety.md](../rules/06_service_safety.md) 驗收：必須實際觸發，不能用查到下次排程時間代替
- **多階段 pipeline（A → B → C）**：綠燈只證明**該階段自己跑完了**，不證明上一階真的寫入或改變了狀態。觸發條件＝任何「前一階失敗、後一階仍能從舊狀態產生正常輸出」的鏈；動作＝**逐階檢查 exit code 與該階自己的輸出**，不可只看最後一階的綠燈。判準：問「如果第一階什麼都沒做，後面幾階的輸出會長得不一樣嗎？」——答案是「不會」就代表綠燈沒有證據力。實例（2026-09-08）：`db.seed_industry` 因原始碼 SyntaxError 中止，但 `fill_weight`／`check_industry`／`pytest 616 passed` 全綠，因為那三個讀資料庫、不讀被改的檔；「所有檢查數字都沒變」看起來像成功，實際意義是**什麼都沒寫進去**。這比一般 bug 危險，因為它讓後續所有資料品質檢查都看似正常。
- **綠燈／零錯誤計數本身也要被驗**：檢查機制吞掉失敗時，綠燈只代表「沒報錯」，不代表「驗到了」。本條決定綠燈能不能當證據：本節的「測試綠」、以及 CLAUDE.md TDD 模式全綠之後的交付，都要先確認驗證機制本身能正確辨識失敗，才算證據；TDD 迴圈什麼時候停不受本條影響。判斷方法：對同一個檢查建立一個預期必須失敗的案例，確認它在預期的斷言上失敗，而不是因為 import 錯誤、收集錯誤或被跳過而失敗；可使用改動前已知會失敗的案例，或刻意注入一個已知錯誤。刻意注入的錯誤，以及要執行的改動前舊版程式碼，都只放在測試替身、`tmp/` 的草稿複本，或另開的 git worktree，不直接改、stash 或 checkout 工作樹原檔：原檔可能被排程從原始碼執行或 import，也可能被健檢的 exe 新鮮度檢查以修改時間讀到，用 hash 確認內容還原，還原不了修改時間。這些位置只防排程執行，不代表非 production：在 repo 內執行仍會讀到正式的 `.env`，是不是 production 照 [06_service_safety.md](../rules/06_service_safety.md) 驗收第 1 步的定義判斷。寫入共用狀態照 Rubric 11；對外發送屬 Rubric 3 必問。必須失敗的案例沒有失敗時，先修驗證機制，再重新驗收。已發生的三種形狀：
  - `xfail(strict=True)` 把**任何**例外都算成預期失敗；當時測試內 SQL 是壞的，什麼都沒驗到照樣綠（2026-08-07）→ 斷言「已知問題仍存在」要用普通 assert 寫明特徵，不用 xfail 作為驗證依據；xfail 表示「預期測試會失敗」，不能證明驗證器本身正確辨識了該問題
  - scraper 讀不存在的欄位回 None、解析也回 None 不拋例外 → 靜默寫入 NULL、parse_errors 永遠是 0（TWSE 零股價格 2016 起全空，2026-08-07）→ 驗 scraper 要抽查目標欄位的非空比例，並先 dump 來源實際 fields 比對欄位名
  - 交易日 gate 把「抓不到 TAIEX」當成休市 → 靜默跳過整條 pipeline 且 exit 0（2026-09-18 整天缺資料）→「合法地沒有」與「沒查成功」必須分開，後者要告警並以非零 exit code 結束（排程器記錄的結束代碼往往是唯一留下的痕跡）；監控門檻在正常日要保持安靜，每天都響的告警會把真失效藏起來
- **修正審查 finding 後**：反查全文有沒有其他段落引用被改動的數值或結論，一併更新後再送複驗；改正本身就是製造錯誤的高風險動作（2026-08-06 策略文件連續三輪複驗，其中兩輪的問題是修正引入的）
- **判定策略「無效益/負向」**：MUST 附**實際失敗的真實案例**（具名交易/受害股 + 進場日 + 報酬 + 失敗機制），不能只給 aggregate（PF/勝率/均值）。理由：均值藏假象——2026-07 判「無 edge」時，是列受害股才發現「-92.7% 崩塌」實為世紀分割的資料假象，改寫了結論。負向結論跟正向採用一樣要交待證據（signal-factory §1a 受害股同精神，延伸到所有策略分析）。

**正例**：v352 採用時附受控對照（同資料、僅 pick+sell_flee 變）＋其餘 4 訊號 bit-identical＋時間前後半雙驗證＋sweep plateau 確認非 overfit（project_v352_baseline）。
**反例**：只看單一訊號 PF 上升就宣告改良成功。合池 PF 才是真實評估，單訊號 PF 升可能是把爛單推給別的訊號（feedback_signal_portfolio_eval）。

## Rubric 3：何時停下來問使用者

> 本 Rubric 的必問/不必問清單，即 CLAUDE.md「Grill-Me 規劃協議」的入樹過濾器：必問類進逼問樹逐題解，不必問類不進樹、自己決定。

**必問（任一命中）**：
- 動作不可逆或影響超出任務範圍：刪檔、改 DB schema、動 production .bat/NSSM 服務、git 破壞性操作、對外發送
- 不確定的套件選擇、架構方向、實作方式（CLAUDE.md 既有規則——這類選錯通常代價高或難回頭）
- 搜尋/嘗試 3 次未果（CLAUDE.md 既有規則）
- 規格有 ≥2 種合理解讀，且選錯會浪費 >30 分鐘的工作
- 發現任務前提可能錯了（要改的東西看起來已被別的機制取代、或需求與既有設計衝突）
- harness 預設與專案規則衝突，而 CLAUDE.md 沒有明示誰優先：不自行猜優先序，當場問使用者並把裁定寫回制度檔（2026-07-25「除非使用者要求否則不要 spawn subagent」與 01_dispatch §1 對撞，裁定結果即 CLAUDE.md「Subagent 授權」節）

**不必問（自己決定、記下理由、繼續）**：可逆、在範圍內、對最終結果無影響的順序/命名/風格類選擇——這類不屬於 CLAUDE.md 說的「技術決策」。

**正例**：殺 Python process 前先確認 parent——使用者機器上有其他 telegram bot 工具會被 cmdline 誤中，環境事實拿不準就問（feedback_process_kill_safety）。
**反例**：「變數名用哪個」「先寫測試還是先寫實作」（結果相同，只是順序）——問了只是把決策成本轉嫁給使用者，這種自己決定。

## Rubric 4：方向錯了該換路（不是重試）的訊號

**任一命中 → 停止此路，換方法或回報**：
- 提案命中 MEMORY.md 的失敗封存條目（標「勿重試/別重提/MUST NOT/已驗證不採用」）→ **直接停**，回報「此方向已封存於 `<memory 檔名>`」；除非使用者明示重開
  - 動手回測任何訊號／防守參數前，先讀該子專案的 memory **檔案全文**，不能只看 MEMORY.md 的索引行：索引行一句話塞不下具體參數結論，只看索引行判斷有沒有命中，正是漏掉封存的破口（2026-07-11 微台 cap 上限 sweep 重現了兩天前已封存的結論）
- 同一方向連 3 個變體都負向 → 前提錯了，不是參數沒調好（此為「變體結果負向」的計數軸，與 [01_dispatch.md](../rules/01_dispatch.md) §5「同一做法**執行失敗**最多重試 2 輪」是不同計數，勿混）
- 打地鼠：每修一個問題冒出一個新問題 → 錯的是架構層不是當前 bug
- 為了讓方案成立，例外條款越加越多（if 特殊情況 A 就跳過、B 再跳過…）

**正例（早該換路）**：momentum_override 連做 11 版（v309–v319）全負才收手。第 3 版全負時就該質疑前提（portfolio dilution 天花板），後 8 版是浪費（project_momentum_override_failed）。
**正例（封存即停）**：flee force-exit 復活已標 MUST NOT——結構性死路（緊 trailing 永遠早於反轉訊號觸發），再聰明的變體都不要試（project_flee_force_exit_revival_failed）。
**反例（不該換路）**：第一次跑就報錯——先讀錯誤訊息、修一次再說。單次失敗不構成換路理由。

## Rubric 5：品質底線怎麼驗（回測改動特化）

採用任何訊號改動前，**全部通過**才算（詳細流程照 skill `signal-factory`，此處是底線清單）：
1. 合池 PF 上升，不只單訊號
2. 時間均勻：前半/後半期各自為正；增益集中在單一事件（2020 崩盤是慣犯）= overfit，不採用
3. 三大目標零違反：勝率、maxL（最大虧損）、交易質量；交易數↑但 PF 不升 = 負向
4. sweep robustness：採用參數落在 plateau 上而非孤峰；掃描曲線單調時**必須**加查時間分布（見 Rubric 1 正例）
5. sanity：未改動的訊號結果 bit-identical
6. **證據品質**（引用任何表格/指標前的前置檢查；前四點由 2026-07 三次踩坑歸納，末點來自 2026-08-05 微台 30m 濾網實驗，詳 memory `project_microtaiex_daytrade`）：
   - 引用 cohort/sweep/regime 表的任何一格前 → **先看該格的 n**；n 小的極端值不得寫進提案，表格產出一律連 n 一起印（RS probe D9 −7.00pp 那格 n<1000，掃 N 才發現符號隨窗口翻轉）
   - **借來的參數不算參數**：沿用他處（別的序列/別的子系統）的最佳窗口前，必須在本序列上重掃，否則挑選理由隨舊用途一起失效
   - 評分系統採用決策 → 必跑**逐年 Δspread 拆解**（零 rebuild）；增益集中單一年份或近年轉負即不採用（ScoreBoard regime 九格近全綠，逐年拆穿增益全在被誤標 bear 的 2021 多頭年，最近兩完整年實為負）
   - 評**攻防/曝險型**改動 → (a) cov/ret/DD/recall 必須同窗 (b) 主指標用**每單位曝險年化**不用累報酬（累報酬單調獎勵曝險） (c) 看 sweep 前先數**差異日與其逐年分布**，差異日 <20 天或集中單一年＝單事件，不採用
   - 單口/單標的系統的 entry filter → dSum 為正 ≠ 濾掉壞單，MUST 比對「**被擋交易損益總和 B**」：真過濾是 dSum ≈ −B；若 B>0（擋掉的是賺錢單）而 dSum 仍>0，增益來自部位機器狀態重排＝噪音

## Rubric 6：背景工作與長指令的完成判定

**觸發**：派背景 agent、跑 `run_in_background`、等任何長指令。（由 2026-07-06／07-07／07-21 三次踩坑歸納）

- **「完成通知」不等於完成**：`run_in_background` 的指令**直接寫本體**，不可再套 `&`／`nohup`／`Start-Process`——雙重背景會讓外層 shell 立即 fork-and-return exit 0，harness 秒發**假完成通知**（PyInstaller 那次 exe 根本還沒覆寫）。harness 自己會背景化並在真正結束時通知。
- **完成判定一律看產出檔實況**（mtime／大小／內容變更），不看 log 的中間字樣（PyInstaller 的「PYZ completed successfully」是中間步驟），不等 agent 自醒。
- **agent 回報「已派出／執行中／等通知」＝角色混淆的空回報，不是進度**：先 `SendMessage` 糾正一次（「你自己就是執行者，沒有別人在跑，立即親自執行原 prompt」），不要急著重派——重派會丟掉它已讀的 context。此為高頻失效模式（2026-07-06～08 至少 8 次）。
- **預期 >10 分鐘的指令不要掛 tool timeout**：曾在 98% 進度被 timeout 精準砍掉，後續兩次 rebuild 完成後 agent 未被喚醒，pipeline 各停擺 18h／5h，靠主對話查產出檔時間戳才發現。（`Start-Process` 式的 detached 啟動**只用於 `run_in_background` 之外**的直接啟動；走 `run_in_background` 時仍照第一條，指令直接寫本體。）

## Rubric 7：驗收對象要在生產路徑上

**觸發**：驗收任何改動、派 agent 審查、宣告「已修好」。（由 2026-08-05／08-06 兩次踩坑歸納）

- **實跑輸出證明「這段程式碼會這樣算」，不證明「使用者看到的是這段程式碼」**。驗收前先確認被改的函式**在生產呼叫鏈上**——曾改完 `analysis/attention_predict.py` 並實跑驗證通過（誤報 26→12 檔），但 Telegram bot 走的是另一個檔，改動全落在只有 CLI 用的 dead path。
- **本 repo 的門檻是多份寫死複製**：離線報表版 `analysis/attention_predict.py` 與 bot 即時版 `telegram_bot/handlers/_attention_predict_intraday.py`（同一款門檻在後者有**三份**複製），**§1／§2①／§3／§5／§13／§14 皆然**。改門檻要搜**數值字面**（如 `100, 25, 500`）而非函式名，只改一份等於沒改到使用者看得到的路徑。
- **餵給驗收 agent 的中介檔**（dump／轉檔／摘要）必須與被驗物在**同一個指令內**同步重建，或讓 agent 直接讀原始檔。兩者不同步會產出看似嚴重、實則不存在的假 finding（.docx 已改對，卻因忘了重 dump 文字版，被回報「修正根本沒寫入」）。

## Rubric 8：受控比對的分母必須自己閉合

**觸發**：任何 controlled comparison、批次重跑、A/B 兩臂實驗。（由 2026-09-11 兩次同型失效歸納：F11 選檔 49 家實際只比 43 家、prose reader 222 家實際只比 215 家）

名詞：母體中的每一家公司恰好一筆 result record；record 的狀態恰好是以下三種之一：受測 reader 的 outcome（如 rescue／unchanged／changed／lost）、`measurement_error`、或非受測 producer 的獨立 stratum（母體取自共用資料表、但該列由別的 producer 寫入）。母體閉合＝`reported_population == count(result records) == sum(各 reader outcome) + count(measurement_error) + count(獨立 stratum)`；獨立 stratum 的列不得歸入本 reader 的 outcome。

四條硬性不變量，驗收時逐條斷言，不以「腳本正常結束」代替：

| 不變量 | 為什麼 |
|---|---|
| `reported_population == count(result records)`（定義見上） | 印出來的總數是母體，不是已比對數。F11 那次「49 家、changed 2」看起來乾淨，而整批立論所依的 8906 花王就躺在未記錄的 6 家裡 |
| `every attempted company == exactly one result record` | 沒有結果的樣本不是「沒事」，是「沒測到」 |
| `measurement_error` 不是 reader outcome | 下載失敗、請求逾時、選不出檔，都不進成效的分子或分母。它說的是實驗沒完成，不是程式的表現。但仍是一筆 result record，計入母體閉合。 |
| progress reporting 不得與 result persistence 共用 failure path | 失敗路徑 `continue` 會同時抹掉結果與進度列印。**失敗本身必須產生紀錄**——observability 不能被它要觀察的那件事關掉 |

★第四條的代價是不可逆的：那次失敗雖然事後用「缺少的進度檢查點」框出了窗口並補齊了每一家的結果，但**原本失敗的是哪幾家**永遠查不回來，因為失敗當下沒有留下身分。閉合能補，身分不能。
**三個實例，同一個形狀——用一個寬鬆的存在性條件冒充完整性判準**（原為獨立踩坑條目，2026-09-11 併入）：

- **受控比對的分母**（2026-09-11）：F11 選檔比對印出「49 家、changed 2」，實際只比了 43 家；prose reader 比對印出 222 家，實際 215 家。失敗路徑 `continue` 既不寫結果也跳過進度列印，而 F11 整批立論所依的 8906 花王正好落在未記錄的失敗裡。補跑後閉合為 222 = rescue 4 + unchanged 217 + measurement_error 1；但**原本失敗的是哪幾家**永遠查不回來——閉合能補，身分不能。
- **「當日有列」不等於抓成功**（2026-08-07）：查三個月漏抓，先只比交易日曆，7 張市場級表 64/64 全到齊；真正的漏抓是**有列但整個市場側欄位全 NULL**（TWSE 四類共 8 個日期），日期層級的檢查完全看不到。→ 查資料完整性 MUST 同時查「每欄位群每日有值檔數 vs 該欄中位數」，且**按市場別分開統計**：多數 scraper 一支同時抓兩市場，單邊失效時另一邊照樣寫入，合併統計會被稀釋掉。
- **「>0 即視為完成」**（2026-08-07）：零股回填用「當日價格筆數 >0」做續跑判定，2580 天跳過 1996 天——歷史每天都有 1–14 筆零星非空殘值，那個門檻被殘值全面誤判。→ 續跑／完成判定 MUST 用**與同列參考欄位的比例**（如 價格筆數 >= 0.8 × 成交量筆數），並先跑一次分布查詢確認乾淨值長什麼樣。

★**診斷腳本的聚合 key 不得比它要主張的單位更粗**（2026-09-12 追加）：
同一輪比對，權威腳本以**公司**逐筆記錄 → 90/90 閉合；診斷腳本以**頁碼**當 key，
同頁多張表互相覆蓋 → 31 家 changed 只印出 25 筆差異，6 家的差異被自己的輸出吃掉。
觸發條件＝寫任何比對／稽核腳本時；動作＝先問「我要主張的單位是什麼」（每家公司的
reader 行為、每個欄位群的每日有值檔數…），聚合 key 至少要等於那個單位，比它粗就會
把 finding 藏起來。這是本 Rubric 第四條的同一個病：observability 不能被它要觀察的
那件事關掉——差別只在那次是失敗路徑吃掉紀錄，這次是 key 碰撞吃掉紀錄。

★**比對與閉合檢查自己的前提也要先驗**（2026-09-12／10-05 追加）：
- **兩臂經過不同序列化路徑**（DB/JSON vs 記憶體物件）→ 先正規化型別與排序再比，並用一組已知應為 unchanged 的樣本 smoke test 比對函式本身。`[('a',1)] == [['a',1]]` 恆為 False，1213 大飲內容相同卻被判 changed（2026-09-12）
- **母體取自共用資料表** → 先查該表有幾個 producer（method／writer 模組）；非受測 producer 的列不計入本 reader 的 outcome，也不剔出母體，獨立成 stratum。1303 南亞等 141 家的列由另兩支 scraper 寫入，曾被誤判 lost（2026-09-12）
- **「每個樣本都要有終局狀態」型檢查** → 狀態集合必須先從被驗 producer 的實際狀態定義與所有產生／回傳路徑確認，不憑印象列舉；補漏列的值標成 validator defect correction，不說成放寬條件。漏列 parse_failed 曾產生 2 家假陽性（2026-10-05）

## Rubric 9：結構化原始碼不以裸字串替換編輯

**觸發**：要修改 `.py`／`.sql`／`.json` 等有語法結構的檔案，而編輯方式是「找一段文字，換成另一段文字」。（由 2026-09-11 一天內五次同型事故歸納）

| 規則 | 為什麼 |
|---|---|
| anchor 必須唯一，`assert count == 1`，**不等於 1 就不寫入** | 這是最便宜也最有效的一道。當天三次被它擋下 |
| anchor 必須是**結構終止符**，不得是段落中段的文字 | 錨在 R025 描述中段那次，若 assert 沒擋住會把該規則後半段整個截掉——那段文字讀起來完全正常，只是少了一半 |
| 不得以「從某定義切到下一個通用標記」為範圍 | 標記不屬於前面那個定義。`_page_text` 與 `_is_aggregate_row` 兩個函式、測試檔的 `HONHAI` 與整條 2317 測試，都是這樣被連帶刪掉的 |
| 寫入後 MUST 驗**結構**，不只驗替換成功 | `count == 1` 只證明「找到了一個地方」，不證明「沒有順手吃掉 tuple、括號、引號或下一段定義」。最低限度：`.py` 用 `ast.parse` 或 import；`.json` 用 `json.loads`；`.sql` 用不連正式資料庫的方式檢查語法（解析器或隔離的非 production 資料庫），不得為了驗語法在正式資料庫執行；migration 要在 `db/migrations` 之外起草與驗證，放進該目錄就等於排定正式寫入（見 Rubric 10）；有 schema 的再跑一次驗證器 |
| 產生含跳脫序列的原始碼時，用檔案寫入而非 shell heredoc | 同日兩次 `\n` 在多層引號間實體化成真正的換行，把 regex 切成兩半（延續 2026-09-08 的 NUL 位元組事故） |
| 寫入含跳脫序列的內容後，以讀 bytes 計數為準（例如用 Python 讀檔後數特定 bytes）；`grep` 只能當有沒有出現的初篩，且 `grep -c` 數的是行數、不是出現次數；不可只用 `sed -n` 目視 | 跳脫序列穿過多層引號會實體化，終端顯示看不出來；2026-09-08 patch 中的 `"\x00"` 落檔成真正的 NUL 位元組，改用 `chr(0)` 並以 bytes 驗 `count(b'\x00')==0` 才乾淨。2026-10-06 實測這台機器：Git Bash 的 `grep -c $'\r'` 不加 `-U` 時，對全 CRLF 的檔回報 0；這個 harness 會把 Bash 指令裡的 `\\` 傳成單一個 `\`，組 pattern 的測試本身也可能錯 |

★**五次事故裡沒有一次是被我自己看出來的**——三次靠 assert、兩次靠 SyntaxError。這是這條規則的真正論據：這類錯誤的產物在肉眼下是通順的，只有機械檢查分辨得出來。

★**最危險的一種不會報錯**：截斷一段規則文字、刪掉一個沒被 import 的函式、拿掉一條測試——語法完全正確，測試可能照樣全綠（`_page_text` 那次 651 個測試裡只有新加的那一條會失敗），而損失要到很久以後才顯現。所以「跑完測試是綠的」不足以證明替換乾淨；要問的是「我這次的替換範圍，有沒有包含我沒打算動的東西」。

## Rubric 10：寫入權是一份合約——範圍、授權、條件、執行都要對上

**觸發**：要做任何有持久效果的動作（DB 寫入、分類／exposure 變更、repo commit、推 main、release、排程狀態、**寫出 migration 檔**），或稽核過去的這類動作。（由 2026-09-15 分類重判追溯稽核歸納：67 家條件未履行、2 家執行超出授權）

| 軸 | 寫入前 MUST 回答 | 違反時的狀態 |
|---|---|---|
| Scope | 這次實際要做的 mutation，每一筆都落在授權的文字範圍內嗎？ | `EXECUTION_EXCEEDS_AUTHORIZATION` |
| Authority | 有明確裁定、對具體提案的同意，或已授權 mutation 的必然連帶嗎？使用者同意的是「對象集合」，還是連 mutation 的「內容」也看過？ | 沒有授權＝provenance gap；只授權集合、內容沒給看＝`AUTHORIZATION_SCOPE_INSUFFICIENT` |
| Condition | 授權附帶的前提／覆核／驗收／順序條件，都在寫入前履行並取得確認了嗎？「暫定裁定」轉成最終了嗎？ | `AUTHORIZATION_CONDITION_UNFULFILLED` |
| Execution | 實際產出的內容和裁定文字一致嗎？執行者、時間、程序和授權模型一致嗎？ | 內容與裁定不同＝`EXECUTION_DIFFERS_FROM_RULING`；執行者／程序不符記入 execution 例外 |

治理結果固定五種（2026-09-15 使用者裁定，不再增生）：`AUTHORIZED`（explicit／batch／rule／consequential）、`AUTHORIZATION_CONDITION_UNFULFILLED`（required_review／acceptance／sequencing／provisional_gate）、`EXECUTION_EXCEEDS_AUTHORIZATION`、`EXECUTION_DIFFERS_FROM_RULING`、`AUTHORIZATION_SCOPE_INSUFFICIENT`。「待裁」是工作狀態，不是治理結果。

- **「繼續／好」不自動等於批次授權**。前一則訊息只列出要處理哪些東西（「剩下 [definition] 14 個」），沒列出要寫成什麼，這個同意只及於對象集合。要寫的是定義文字、分類、權重這類內容時，MUST 先把內容給使用者看。
  - 反例：09-04 對「剩下的 [definition] 14 個」說「繼續」，19 個節點的定義文字事前沒給看就 commit（`1cfa2801`、`739e77be`）。
  - 反例：09-03 V1 裁定名稱「半導體／電子零組件通路」，寫入的是「半導體通路（含設備與材料）」；事後揭露不會消掉這個差異。

- **條件是授權本體的一部分**。選項說明裡寫「列給你覆核」「修完再送 read-back」「先出草案給你看」，就要先交付那個產物、得到回應才寫入。事後沉默不算履行；事後補審是另一個補救動作，不得改寫當時的授權紀錄。條件類型記為 precondition／required_review／acceptance／sequencing。
  - 正例：09-06 16:40「先出草案給你看，不直接改 DB」→ 又問了三題、使用者逐題選完才 commit `d1a80ce0`。
  - 反例：09-10 選「完整遷移，39 列逐列讀證據裁定」（附「把名單列給你覆核」），實際 129 列機械判、名單沒交付，就寫進 DB 了。
- **後來被覆蓋、修正或重讀，只改變資料現況，不回溯消除當時 execution 的治理判定**。稽核時先判當下那一筆寫入，再另外記它現在的狀態。
  - 例：09-08 15:35 在「先修程式，再重跑」授權下，對不在 84 家內的 6166 用正式 DB 跑 scraper → `EXECUTION_EXCEEDS_AUTHORIZATION`，不因之後重讀而撤銷。
- **範圍比條件更嚴**。授權說「轉 Core pending 並記成缺口」，就不能執行成「整筆移除 exposure」。範圍外的 mutation 要先停下來另外取得授權，不能用「反正結果合理」補正。
  - 反例：`d1a80ce0` 把友威科、天正國際整筆移除。
- **連帶的結構性維護**（key 對齊、正規化、外鍵修補）如果**沒有語義影響**，可以沿用 parent 授權，但 MUST 在當下記錄 parent mutation；有語義影響的連帶變更（改分類、權重值、節點）要另外取得授權。
  - 例：1341 富林-KY 的 weight_item 隨 NFKC 正規化改成「PU/TPU」，parent 是 09-10「成因 1＋2 寫入資料庫」。
- **寫出 migration 檔就是排定正式 DB 寫入**：`db/connection.py init_db()` 會在任何 cron／daemon 啟動時自動套用 `schema_migrations` 裡沒有紀錄的 SQL。所以建立 migration 檔前就要取得「最終 DB mutation」的授權，不是只取得「寫一個檔」的授權；稽核時「寫檔者」和「套用者」要分開追。
  - ★**繞過 `init_db` 手動執行 migration（`cur.execute(open(sql).read())`）又不登記，會被執行兩次**：108–112 都是寫檔當下在 session 裡直接跑，沒寫 `schema_migrations`，之後 snapshot daemon、intraday_publish、ftse_txf_update 的 `init_db` 把它們當成待套用又跑一次才登記。DDL 冪等無害，但 DML（108 的 DELETE 與狀態 UPDATE）是真的第二次寫入。觸發＝要在 session 內套用 migration → 動作＝呼叫 `init_db()`（它會登記），不得直接 execute 檔案內容；稽核時 `applied_at` 只證明「何時被登記」，實際生效時間要用資料本身的時間戳交叉比對。
- 稽核工具 MUST 把選項題回答當成使用者決定，並讀選中選項的**完整說明**，因為條件寫在說明裡，不在標籤裡。回答有**兩種格式**：`Your questions have been answered` 與 `The user answered`（後者常是使用者自己打的長篇裁定，條件就在那段文字裡）；只認前者會漏掉 V1、A2-12、B2 這類分支裁定（2026-09-15 查證）。最穩的做法是以 `tool_use_id` 對回 AskUserQuestion 呼叫，不靠前綴字串。
- **DB 現況不等於裁定現況**：寫入要另外取得授權，所以「已裁定但還沒寫入」的對象在 DB 上和「從未裁過」看起來一樣。建立新裁定、重新分流或新建紀錄前，先查既有的裁定紀錄（裁定檔、ledger），命中就照既有裁定處理，不重複建案；除非使用者明示重開該裁定。
  - 例：2026-09-22 把 3178 分流成 CANDIDATE，實際 pilot 已有 2026-09-16 的裁定（細節見 memory `project_industry_rejudge`）。

## Rubric 11：跑任何可能寫入共用狀態的指令前

**觸發**：要執行的腳本或測試可能寫入 DB、repo 內或 repo 外的共用／持久產出、production 資料，smoke test 與驗證用測試也算——「只是測試」不改變它寫的是哪裡。與 Rubric 10 的分工：Rubric 10 管「有沒有寫入權」，本 Rubric 管「不打算寫入時會不會意外寫入」。

| 規則 | 為什麼 |
|---|---|
| 先讀腳本的進入點與參數解析，確認旗標真的被解析、`__main__` 會呼叫什麼；不可用 memory／文件的描述代替讀檔 | 2026-08-14 依 memory 跑 `db.seed_themes --check`，該檔沒有 argparse，未知旗標被靜默忽略，把已清空的 themes 表灌回 33 題材／231 對照；未被解析的旗標＝直接執行本體 |

| 「必須成功」型的破壞性對照測試不依賴 `finally: rollback` 收尾：執行前先確認測試使用的 transaction／連線不會 commit 到受保護的共用或 production 狀態；可用單一連線、SAVEPOINT／transaction rollback 等明確邊界驗證 constraint，測完再查 count／關鍵狀態確認沒有殘留並清理。被驗的 constraint 若是 `DEFERRABLE INITIALLY DEFERRED`（例：`industry_tree_leaf_guard`，migration 097），違規通常延後到 transaction commit 時檢查；若違規操作在檢查前已由 SAVEPOINT／rollback 撤銷，trigger 不會因此執行，測試可能只得到「沒報錯」。要在同一個 transaction 內、受測操作全部做完之後下 `SET CONSTRAINTS ALL IMMEDIATE`，才看得到檢查結果；先下會退回逐句檢查，多步驟的合法操作（例如拆分有成員的葉節點）會在第一步被誤報。合法操作也一樣，沒設 IMMEDIATE 時的「沒報錯」不代表 guard 放行（2026-10-09 於隔離容器實測，PostgreSQL 16.13） | 2026-09-03 正例那半 commit 進 production，30 列 V1 曝險被搬到測試節點；rollback 在 commit 之後是 no-op |

## 誠實條款

拆解、驗證、多樣本評審補得了**執行品質**；**模糊題與品味判斷**補不了。遇到品味題（該不該採用、兩個都對選哪個、命名/文案/美感）依序：
1. 派 **fresh-context 對抗審查**（model 用 `opus`；主模型即 opus 時是平調，價值在對方沒有沉沒成本），prompt 附正反雙方論據
2. 仍拿不準 → 生成 2–3 個獨立答案，派 fresh agent 評審選優
3. 仍分歧 → 明說「這題超出我能可靠判斷的範圍」，附選項與 tradeoff 給使用者裁決

禁止假裝有把握。錯誤的自信比「我不確定」貴得多——尤其在這個專案，一個錯誤採用會污染之後所有版本的 baseline。
