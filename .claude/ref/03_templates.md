# 03 派工 Prompt 模板

> 按需讀取檔。要寫派工 prompt 時讀，配合 `.claude/rules/01_dispatch.md` 使用。
> `【】`是填空。範例中的檔名與情境是示意，派工時以當下實況為準。

## 每個 prompt 都要有的東西

- 五段：背景與動機／目標／範圍（含「不要做」）／驗收條件／回報格式
- **agent 看不到你的對話歷史**，`Explore` 與 `Plan` 連 CLAUDE.md 與 rules 都看不到。它需要的背景全部寫進 prompt，路徑寫絕對路徑。
- 其他型別的 agent 會載入 CLAUDE.md 與常駐 rules，但載入的是 **session 開始時的版本**。被驗物若是本 session 改過的制度檔，prompt 要明寫「從磁碟 Read 下列路徑，不要依你 context 裡已有的版本」。
- 回報格式永遠包含這兩句：「不確定處明確標注」「長產物寫到 `c:\Claude\Invest\tmp\【子目錄】\`，回報只傳路徑」
- Agent tool 呼叫時顯式傳 `model` 與 `effort`（每個模板標題都寫了該傳什麼；依據是 01_dispatch §3）
- 驗收與審查類的 prompt **不可**出現「應該沒問題」「我認為已完成」「確認一下」這類引導語，也不要描述實作過程

## 送出前自查（30 秒）

1. 一個完全不知道前情的人，只讀這份 prompt，知道要交什麼嗎？
2. 驗收條件能不能機械判定？（「找全」不行；「每個呼叫點列 檔案:行號，預期 X 目錄至少一處」可以）
3. 有沒有寫「不要做什麼」？
4. 回報長度有沒有上限？
5. 會改檔或上網的 agent，使用者同意了嗎？（CLAUDE.md「Subagent 授權」）

## T1 搜尋／探勘 — `subagent_type: Explore`、`model: sonnet`、`effort: medium`

```
背景：【為什麼要找這個，找到後要拿來做什麼】
目標：【要找什麼——定義、呼叫點、慣例、資料流】
範圍：搜 【絕對路徑的目錄/glob】；不需要讀 【排除範圍，如 build/、dist/、tmp/】
驗收：【怎樣算找全——如「所有 import 此模組的檔案」「我預期 X 和 Y 目錄至少各一處，若沒有請明說」】
回報：條列「檔案:行號 — 一句話說明」，每條 ≤2 行；找不到就回報「未找到」＋已搜過的 pattern 清單；不確定處明確標注；總長 ≤40 行
```

**範例**：
> 背景：要把 buy 訊號的防守參數改成 per-signal，需要先知道現在防守價在哪些地方被計算與消費。
> 目標：找出 `pos_defense_price` 的所有寫入點與讀取點。
> 範圍：搜 c:\Claude\Invest\signal_backtest\ 與 c:\Claude\Invest\signals\；不需要讀 tmp/、logs/。
> 驗收：每個寫入／讀取點都列出；我預期 factories/ 內至少有寫入點，若某訊號檔完全沒有請明說。
> 回報：兩節「寫入點」「讀取點」，各條列 檔案:行號 — 一句話；總長 ≤40 行。

## T2 實作 — `subagent_type: general-purpose`、`model: sonnet`、`effort: high`（先問使用者）

```
背景與動機：【要解什麼問題、為什麼現在做】
目標：【具體改什麼，一句話】
作法：【已確立的方案；有參考實作就給 檔案:行號】
範圍：只改 【檔案清單】；不要動 【明確排除——周邊重構、格式、其他訊號】；不要 commit
驗收：【可機械判定——測試指令與預期結果 / 實跑指令與預期輸出】
回報：改了哪些檔（檔案:行號 + 一句話）、驗收指令的實際輸出原文、不確定處；diff 大就落檔傳路徑
```

**範例**：
> 背景與動機：sell_flee 的 give-back 出場要加停滯天數參數，目前寫死 5 日，要 sweep 用。
> 目標：把 `_transient_giveback_exit` 的停滯窗口抽成參數 `stall_win`，預設 5，行為不變。
> 作法：參考 c:\Claude\Invest\signal_backtest\factories\_conditions.py 內該 helper 現有簽名，加 keyword 參數即可。
> 範圍：只改 _conditions.py 與其兩個呼叫點（pick、sell_flee）；不要動其他訊號、不要改任何門檻值；不要 commit。
> 驗收：照 skill signal-factory 的跑法跑 sell_flee，結果與改前 bit-identical。
> 回報：改動點 檔案:行號、驗收輸出中的 PF／交易數原文、任何不確定處。

## T3 重構 — `subagent_type: general-purpose`、`model: sonnet`、`effort: high`（先問使用者；設計拿不準先派 `Plan`）

```
背景與動機：【現在的痛點；為什麼值得動】
目標：【重構後的形狀】
不變量：【行為必須完全不變的部分＋怎麼證明——測試、bit-identical 對照、輸出 diff】
範圍：【檔案清單】；不要順手改 【格式、命名、無關 dead code】；不要 commit
驗收：【不變量的證明指令＋預期結果】
回報：結構前後對照（簡述）、驗收輸出原文、被迫做的取捨、不確定處
```

**範例**：
> 背景與動機：六個 factory 檔各自複製了 K 棒 helper，改一處要同步六處，已經漏改過。
> 目標：抽到 _conditions.py 共用，六檔改 import。
> 不變量：六訊號回測結果 bit-identical（這是硬證明，不是「邏輯相同」）。
> 範圍：factories/ 六檔 + _conditions.py；不要動門檻值、不要改既有命名風格。
> 驗收：重構前先跑一次存檔，重構後再跑，diff 為空。
> 回報：搬了哪些 helper（清單）、diff 結果原文、若有無法統一的差異逐條列出。

## T4 研究 — `subagent_type: general-purpose`、`model: sonnet`、`effort: high`（先問使用者；結論要拿來做高風險決策時改 `model: opus`）

```
背景：【要回答什麼決策；答案會怎麼被使用】
問題：【具體問句，可多個，編號】
來源優先序：【官方文件 > 原始碼 > issue/論壇；本專案內部問題則 repo 優先】
限制：對外請求不得包含使用者姓名、email、專案名稱
驗收：每個結論附來源（URL 或 檔案:行號）與支持它的原文片段；查不到的明說「查無」並列出查過哪裡，不得推測補位
回報：每個問題一節：結論一句話 + 證據 + 信心（高/中/低與原因）；總長 ≤50 行，細節落檔傳路徑
```

**範例**：
> 背景：想把盤中 sweeper 從輪詢改成 websocket，需先確認 SDK 支援度，答案決定要不要立案。
> 問題：(1) 目前安裝的版本是否支援 tick websocket 訂閱 200 檔以上？(2) 斷線重連是 SDK 內建還是要自己寫？
> 來源優先序：官方文件與 SDK 原始碼（site-packages 內）優先，部落格文章僅作線索。
> 驗收：每個結論附文件 URL 或原始碼 檔案:行號；查不到就寫「查無」。
> 回報：兩節，各為 結論＋證據＋信心；總長 ≤50 行。

## T5 對抗審查 — `subagent_type: general-purpose`、`model: opus`、`effort: high`（高風險決策用 `xhigh`；唯讀所以自動授權）

fresh context：prompt 不含實作過程、不含你自己的結論。你自己就是 opus 時照派，價值在對方沒有沉沒成本。

```
背景：【被審物是什麼、要用在哪、錯了會怎樣】
被審物：【絕對路徑清單 或 diff 範圍（如 git diff main）】
審查面向：【正確性 / 規則互打 / 路徑與名稱真偽 / 邊界情況 /【任務特定面向】】
立場：你的任務是找出問題，不是確認沒問題。每個面向至少主動嘗試反駁一次。
限制：唯讀。不得修改任何檔案，不得執行會寫入檔案、資料庫或對外發送的指令。
驗收：每個 finding 附 位置（檔案:行號）+ 為什麼是問題 + 建議修法；逐面向回報「查過什麼、發現 N 項」，不可整體一句「沒問題」帶過
回報：依嚴重度排序（會壞 > 會誤導 > 可改進）；沒有 finding 的面向要說明查了什麼所以排除；不確定處明確標注
```

**範例**：
> 背景：制度檔剛改完，未來所有 session 都會依它行動，錯誤會被長期放大。
> 被審物：c:\Claude\Invest\CLAUDE.md、c:\Claude\Invest\.claude\rules\ 下四檔、c:\Claude\Invest\.claude\ref\ 下各檔。
> 審查面向：(1) 規則互相打架 (2) 檔案路徑／工具名／模型名是否真實存在 (3) 較弱的模型會誤讀的模糊語句 (4) 路由表有沒有斷鏈。
> 立場：找問題，不是背書。每檔至少提出一個「這句會被怎麼誤讀」的嘗試。
> 限制：唯讀。
> 驗收：finding 附 檔案:行號 + 誤讀方式 + 修法。
> 回報：依嚴重度排序；每個面向都要有「查了什麼」的交代。

## T6 驗收 read-back — `subagent_type: Explore`、`model: sonnet`、`effort: medium`（唯讀，自動授權）

```
請完整讀完下列檔案（不要只讀片段），逐條回答驗收清單。
檔案：【絕對路徑清單】
驗收清單：
1. 【可判定的條件，如「檔案存在且非空」「含有 X 節」「所有 markdown 連結指向的檔案都存在」「沒有出現字串 Y」】
2. 【…】
限制：唯讀，不得修改任何檔案。
回報：每條一行「通過／不通過 — 證據（檔案:行號或原文片段）」；不通過的條目說明差在哪；有任何你覺得奇怪但不在清單上的地方，列在最後「清單外觀察」
```

**範例**：
> 請完整讀完 c:\Claude\Invest\.claude\rules\02_judgment.md，逐條回答：
> 1. 是否有 Rubric 1 到 12，編號連續無缺？
> 2. 每個標 ★ 的 Rubric，在 c:\Claude\Invest\.claude\ref\02_cases.md 是否有同編號的節？
> 3. 檔內每個相對連結指向的檔案是否存在？
> 限制：唯讀。
> 回報：每條一行 通過／不通過 — 證據。

## T7 多答案評審（誠實條款第 2 步）— `subagent_type: general-purpose`、`model: opus`、`effort: high`（唯讀，自動授權）

先各自獨立產出 2–3 個答案（分別派 fresh agent，彼此看不到對方），再派一個評審：

```
背景：【要決定什麼；決定錯了的代價】
候選答案：【A／B／C 的全文或檔案路徑；不要標示哪個是誰寫的、哪個是原方案】
評審標準：【依重要性排序的 3–5 條可判定標準】
限制：唯讀。
回報：每個候選對每條標準的評語（一句話）＋排名＋「若我必須反對第一名，最強的理由是什麼」；若標準不足以分出高下，明說「無法區分」而不是硬選
```
