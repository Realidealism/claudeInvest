# Fable 工作手冊：規劃、拆步驟、檢查

寫於 2026-11-17（Fable 5.2），給之後接手這個專案的模型。

## 這份手冊管什麼、不管什麼

CLAUDE.md「每個任務的骨架」規定每個任務要經過哪七站，Rubric 1–12 與 01_dispatch 規定每一站的底線。它們回答「什麼情況要停、什麼不能做」。沒寫的是站與站之間怎麼想：一句請求怎麼變成計畫、計畫怎麼切成步驟、做完之後怎麼知道真的做完。這份手冊只寫那一段。

**本手冊不管的事**：該不該問使用者、有沒有權寫入、能不能派 agent、派工 prompt 怎麼寫、怎麼送獨立驗收、計畫交在哪裡。這些的判準只有一份，在 CLAUDE.md、`.claude/rules/`、`.claude/ref/` 與 memory。本手冊提到它們時只寫出處，不轉述內容；要用就去讀原文。

使用前提：

- 本手冊不授予任何權限，也不放寬任何規則。內容與 CLAUDE.md、`.claude/rules/`、`.claude/ref/`（含標 ★ 的 Rubric 的細節節）、memory 裡的工作偏好、封存與授權條目、或使用者裁定衝突時，以它們為準，並把衝突的兩段原文回報使用者。
- 本手冊裡「可以停、可以繼續」的句子，只在制度沒有另外要求時成立。制度規定必讀、必問、必等、必驗的事照制度做，本手冊的任何條件都不能取消它。
- 本手冊只給主對話用。你若是被派出的 subagent：不要照本手冊操作，照 CLAUDE.md「你若是被派出的 subagent」節與派工 prompt 做。

## 1. 規劃：從請求到計畫

依序做 1.1 到 1.6。小任務每一步只要一兩句話，但每一步都要有答案。

### 1.1 先寫出完成狀態

探勘之前，先用一句話寫出「完成時什麼是真的」，寫成別人可以檢查的事實；探勘之後修正它。任務做到一半才載入本手冊，就在載入當下寫。這句話放進給使用者的確認問題或計畫裡，不另外當成開場白。

- 請求「修掉某個告警的誤報」→ 完成狀態「對〈觸發誤報的那筆輸入〉不再告警；對〈一筆本來就該告警的輸入〉仍然告警；bot 實際走的那條路徑也是如此」。
- 反例：「把誤報修好」。這句沒有說怎麼檢查，也沒有說不能把該發的告警一起關掉。

寫不出這句話，表示還不知道任務是什麼，先去查或去問。

接著數請求裡有幾件事。使用者常在一則訊息裡交代三四件（寫一份東西、存到某處、再檢查另一個檔）。每一件各自有完成狀態，最後的回報逐件交代。

### 1.2 判斷任務類型

類型決定交付物長什麼樣。

| 類型 | 交付物 |
|---|---|
| 查詢、解釋 | 答案，附 檔案:行號 或輸出原文；把「查到的」和「推論的」分開寫 |
| 單點可逆修改 | 改動＋實跑輸出 |
| 持久寫入（DB、分類、migration、commit、排程） | 寫入＋寫後逐項比對 |
| 採用判斷（該不該採用、兩個選哪個） | 建議＋證據＋不確定處。交付的是判斷，不是改動 |
| 設計、制度檔修改 | 草案＋審查結果 |

一個請求常混兩類。「把門檻調好然後上線」是採用判斷加持久寫入：拆成兩段，各自交付。前一段得出「建議採用」，不等於後一段可以寫入。

每一類要過哪些閘門，這張表不列，照制度。這張表的類型也與「瑣碎／非瑣碎」無關。

### 1.3 帶著問題去探勘

探勘分兩種，先分清楚。

**制度規定要讀的**（掃封存、訊號工廠主題索引、子專案 memory 檔全文、標 ★ 的 Rubric 的細節節、要跑的腳本的進入點等），不在本節的取捨範圍內，一律照制度讀。下面的停止條件不適用於它們。

**你自己決定要查的**，才用下面的做法。探勘之前先列出「答案會改變計畫」的問題，通常 2 到 5 個。常見的幾個：

- 要改的東西在哪裡，有幾份複製
- 它由誰呼叫，在不在服務、排程、bot 指令往下的呼叫鏈上
- 有沒有既有機制已經在做這件事
- 驗證手段存不存在：有測試嗎、能實跑嗎、實跑會寫到哪裡

停止條件（只管你自己列的問題）：剩下的未知數不論答案是哪一個，計畫都一樣，就停止探勘。反過來，探勘到一半問題清單越列越長，表示任務比原先以為的大，回 1.1 重寫完成狀態，再看 1.5。

### 1.4 列出假設，找最貴的那一個

把計畫依賴的每個假設寫下來，各標一個來源：

1. 本 session 親眼看到的（工具輸出、讀到的檔案內容）
2. agent 回報的
3. memory 寫的（寫入當時為真，現在可能已經不是）
4. 推論出來的

標來源的用途是：回報時不把第 2、3、4 種寫成已查證的事實。agent 回報要怎麼核對才能據以動手，照 01_dispatch §4。

然後問：哪一個假設錯了，整個計畫就白做？把驗證它排成第一步。

例：計畫假設「改 `analysis/` 下某個函式，bot 的輸出就會跟著變」。這個假設錯了，後面全部白做，而且驗收還會通過（Rubric 7 的反例就是這個形狀）。所以第一步是從 bot 指令往下追呼叫鏈，不是改檔。

查得到的假設自己查。查不到、屬於使用者的偏好或取捨的，照 CLAUDE.md 的 Grill-Me 協議與 Rubric 3 處理。

### 1.5 估範圍

`.claude/ref/05_letter.md` 明講制度補不了「這整件事是不是太大」的判斷。下面三個訊號可以代替那個判斷的一部分：

- 寫得出每一步的驗證，卻寫不出整件事的驗收方式
- 後面的步驟要等前面的結果出來，才寫得出內容（不是順序相依，而是連要做什麼都還不知道），而且後面那段含持久寫入或大範圍改動
- 完成狀態那句話用「並且」連接了兩個可以各自交付的東西，而使用者沒有要求一起交付

任一出現，就在交給使用者的計畫或確認問題裡提出：建議先做能獨立驗收、做完本身就有用的最小一段，並列出延後的部分。這是提議，範圍由使用者決定。使用者在一則訊息裡交代多件事，本身不算命中。

### 1.6 計畫裡要有什麼

計畫交在哪裡、需不需要批准，照 CLAUDE.md。這裡只講內容：

```
完成狀態：<一句可檢查的事實；多件事就多句>
不做：<明確排除的相鄰事項>
假設：<每條標來源 1–4；不確定的關鍵假設在動手前確認：列為最前面的步驟，或列為要問使用者的問題>
步驟：
  1. <動作> → 產出 <什麼>
     驗證：<跑什麼；對的時候看到什麼；錯的時候看到什麼>
  2. ...
完成證據：<最後要貼給使用者的是哪幾段輸出>
```

「錯的時候看到什麼」是最容易被省略的一格。填不出來，表示這個驗證不可能失敗，也就不是驗證（Rubric 2「綠燈本身也要被驗」）。

## 2. 拆步驟

### 2.1 一步是什麼

一步＝一個產出＋一個驗證＋做完可以安全停下。用三個問題檢查切得對不對：

- 能不能用一句話說出這步做完之後多了什麼。「了解呼叫關係」不是產出；「列出 N 個呼叫點的 檔案:行號」是。
- 這步失敗時，看得出是這步壞的，還是前面某步壞的。
- 做完這步之後 session 斷掉，工作樹和 DB 處在說得清楚的狀態。

任一題答不出來，就再切細，或把兩步合成一步。

### 2.2 在哪裡切

下面這些位置一定切開：

- **動作性質改變的地方**：唯讀 → 寫暫存檔 → 寫共用狀態 → 對外發送。不要讓一步橫跨兩級。每跨一級之前，回頭查制度對那一級的要求（Rubric 3、10、11），不憑印象。
- **「產出要寫入的內容」和「寫入」之間**：切成兩步。兩步之間要不要停、要誰確認，照 Rubric 10。
- **派給別人做的部分**：一個 agent 一個交付物。同一份 prompt 既要它找又要它改，回報會把兩件事的不確定處混在一起。

### 2.3 排順序

使用者鎖定的順序是硬約束（Rubric 10），不重排。沒有被鎖定的部分，依這個優先序排：

1. 依賴關係：產出被後面用到的排前面。
2. 可能推翻計畫的排前面：1.4 找到的最貴假設、可行性探針。便宜的失敗要早發生。
3. 唯讀排在寫入前，可逆排在不可逆前，repo 內排在對外前。
4. 檢查工具排在被檢查的改動前：要靠某個測試或腳本判定成敗，先確認它遇到錯的輸入會失敗（Rubric 2），再做改動。

### 2.4 執行中維持三欄狀態

每到一個里程碑，要答得出三欄：已確認的（各附證據在哪）、仍是假設的、還剩什麼。CLAUDE.md「回報風格」的里程碑節點要回報的是第一欄與第三欄；第二欄是本手冊加的，用來防止把假設當成事實回報。

長任務的對話會被自動摘要，摘要後細節會失真。只存在腦中、沒寫進回覆或檔案的結論，要當成之後會不見。跨對話任務的進度記在哪裡、何時清理，照 CLAUDE.md「記憶與跨對話任務」。

### 2.5 步驟失敗、計畫被推翻時

- **失敗**：先讀錯誤訊息原文，用一句話說出原因，再動手改。說不出原因就繼續蒐集證據，不要改了再試。重試次數照 01_dispatch §5；結果連續負向照 Rubric 4。這是兩個不同的計數。
- **不可以用來讓步驟通過的做法**：修改檢查讓它通過、縮小檢查範圍、把失敗的樣本排除在外。檢查本身有錯就明說，把「修檢查」列為獨立的一步，修完先確認它仍會在錯的輸入上失敗。
- **新事實出現時**：使用者已經確認或批准的任何內容，有沒有因此需要改變？有 → 停下，回 1.1 重寫，照 CLAUDE.md 回報節點 3、4 向使用者說明並列出選項，等使用者裁定。拿不準算不算改變，當成有。
- **審查不收斂**：同一份設計連 2 輪審查都「修一個、冒一個」→ 不再逐條補，照 Rubric 4。
- **途中發現任務範圍外的問題** → 記下來，在回報裡提出，不順手修（CLAUDE.md「改動原則」）。

## 3. 檢查自己的成果

本節是自查。自查不代替獨立驗收：自查做完，照 01_dispatch §6 送驗。自查的用途，是不讓驗收者把時間花在你自己抓得到的問題上。

### 3.1 回到原請求

重讀使用者的原始訊息，不是重讀自己的計畫，因為計畫在執行中可能已經偏離。對 1.1 數出來的每一件事（開工時沒數，就現在從原始訊息逐件數），各指出交付物在哪、證據在哪。沒做完的那一件要明寫沒做完和原因。

### 3.2 每個主張配一個證據

把回報草稿裡的每個主張列出來，逐一回答：這是我在本 session 看到什麼而知道的？來源等級同 1.4。

- 草稿裡出現「應該」「理論上」「照理說」的句子，都是沒有證據的主張。去取得證據，或改寫成「未驗證」。
- 數字從工具輸出抄，不憑記憶寫。會被加總的數字自己重加一次，確認分母閉合（Rubric 8）。
- 修 bug 要說得出根因，並解釋舊行為為何發生（Rubric 2）。

### 3.3 確認檢查不會騙你

對每一個要拿來當完成證據的檢查，問兩個問題：

- 如果我的改動完全沒有生效，這個檢查的輸出會不一樣嗎？不會，它就沒有證據力。多階段流程逐階問（Rubric 2 的多階段 pipeline 那一列）。
- 我有沒有看過它失敗？沒有就照 Rubric 2「綠燈本身也要被驗」那一段處理。

另外過一次 Rubric 7：被改的東西是否在生產路徑上。

### 3.4 結果好得不尋常時，先懷疑

PF 大幅跳升、錯誤數是零、比對 100% 一致、一次就全綠，都屬於這一類。判斷方式：結果比你開工前預期的好，或好到沒有任何例外。遇到時，回報之前依序查：

1. 輸入是不是空的或舊的：看筆數 n、檔案 mtime、資料日
2. 分母有沒有閉合，失敗的樣本是不是被跳過了（Rubric 8）
3. 對照組有沒有被一起改到；未改動的部分是不是 bit-identical（Rubric 5 第 5 點）
4. 增益集中在哪裡：單一事件、少數幾筆交易（Rubric 5 第 2 點）；差異日集中在單一年（Rubric 5 第 6 點）

四項都過，只表示結果沒有這四種常見的假象，可以照實回報。它不是採用判準：該不該採用，照 Rubric 1 與誠實條款，訊號／評分／攻防的改動另照 Rubric 5 全部六點。這四項的用途，是把「聞得出增益來源不乾淨」的直覺換成可以機械執行的檢查。

### 3.5 回報分三類寫

- **已驗**：附輸出原文（要附哪些行，照 CLAUDE.md「回報風格」）
- **未驗**：為什麼沒驗
- **驗不了**：需要什麼條件才驗得了

有未驗或驗不了的項目時，不把整件任務說成完成（Rubric 2）；能驗而還沒驗的，去驗，不列為未驗。把未驗的東西寫成已完成，使用者會據以做下一個決定，之後的每一步都建在上面。

## 4. 最常重複的三種錯

`.claude/ref/00_diagnosis.md` 在 2026-11-11 統計過當時的踩坑紀錄，重複出現的是下面三種形狀：審查不收斂 3 條、授權邊界 2 條、驗收器設計 2 條。它的診斷是，事發當時對應的 Rubric 都已經存在，但條文埋在很長的檔案裡，等於沒被讀到。下表列出每一種會在本手冊的哪一節碰到，碰到時去讀右欄的規則原文：

| 形狀 | 本手冊 | 規則 |
|---|---|---|
| 審查「修一個、冒一個」，不收斂 | 2.5 | Rubric 4 |
| 寫入越過授權邊界 | 2.2、2.3 | Rubric 10 |
| 驗收器本身有洞，綠燈沒有證據力 | 2.3 第 4 點、3.3 | Rubric 2 |

做不到或判斷不了的時候，照誠實條款明說，把選項與取捨交給使用者。「我不確定」「這題我判斷不了」在這個專案是可接受的答案。
