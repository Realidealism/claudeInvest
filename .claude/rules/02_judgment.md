# 02 判斷力 Rubrics（常駐核心）

每條＝**觸發 → 動作**。本檔每個 session 都載入，所以只寫判準；事故經過、完整表格、狀態碼在細節檔 `.claude/ref/02_cases.md` 的同編號節。

- 標 ★ 的 Rubric：命中觸發而且要動手時，**先 Read 細節檔該節再動手**（那幾條的細節多到核心裝不下，照核心摘要做會漏）。
- 沒標 ★ 的：照本檔做即可。
- 分工：本檔負責觸發條件、必做的動作、不可違反的限制；細節檔負責完整條件、例外、事故證據。**兩邊互相矛盾 → 暫停與該 Rubric 相關的操作，把兩邊原文並列回報使用者；不自行挑一份當權威。**
- Rubric 編號是固定的（memory、skill 都用編號引用），不可重排。

## Rubric 1：何時升級模型／找第二意見

**觸發（任一）**：
- 問題是「取捨」不是「執行」：多個方案各有利弊，或驗收標準本身還沒被定義
- 數字都算對了，但「該不該採用」拿不準（統計顯著還是過擬合、增益來源乾不乾淨）
- 同一子任務失敗 2 次，且兩次原因**不同**（原因相同是執行問題，修就好）

**動作**：派 fresh-context 對抗審查（做法見 [01_dispatch.md](01_dispatch.md) §5、§6）。

正例：門檻 sweep 結果單調遞增，機械上該採最緊值，但增益全來自 2020 崩盤的幾筆單——這是該不該採用的問題，派第二意見。
反例：把已驗證的條件複製到另一個訊號再跑回測——純執行，不升級。

## Rubric 2：何時算「真的完成」

完成＝**驗收證據在手**，不是「我改完了」。依類型：

| 做了什麼 | 要有什麼證據 |
|---|---|
| 程式碼 | 測試或實跑的輸出原文貼在回報裡。回測改動：六訊號全跑完＋未改動的訊號結果 bit-identical |
| 檔案／文件 | fresh agent read-back 通過（[01_dispatch.md](01_dispatch.md) §6） |
| 修 bug | 說得出**根因**，並解釋舊行為為何發生。「改了之後不再出現」不算 |
| 排程／服務 | 實際觸發一次，或查到下次排程時間。看門狗必須實際觸發（`06_service_safety.md`） |
| 多階段 pipeline（A→B→C） | 逐階看 exit code 與該階自己的輸出。自問：「如果第一階什麼都沒做，後面幾階的輸出會不一樣嗎？」不會＝最後的綠燈沒有證據力 |

**綠燈本身也要被驗**（要拿綠燈或零錯誤計數當完成證據之前必做，TDD 全綠之後的交付也算）：
- 對同一個檢查造一個「必須失敗」的案例，確認它在**預期的斷言**上失敗，不是因為 import 錯誤或被跳過。沒失敗就先修檢查機制。
- 注入的錯誤與舊版程式碼只放測試替身、`tmp/` 複本或另開的 git worktree，**不直接改、stash、checkout 工作樹原檔**（排程會從原始碼執行）。
- 上面那些位置只防排程執行，**不等於非 production**：在 repo 或 worktree 內執行仍會讀到正式的 `.env`。會寫 DB／共用產出的照 Rubric 11，會對外發送的屬 Rubric 3 必問。
- 不用 `xfail` 當證據（它把任何例外都算成預期失敗）。
- 驗 scraper：抽查目標欄位的非空比例，先 dump 來源的實際欄位名比對。
- 「合法地沒有」與「沒查成功」要分開：後者要告警並以非零 exit code 結束。
- 寫驗收器的自我測試：輸入的路徑、副檔名、參數形狀照正式呼叫實際傳入的樣子建，不另取方便的名字。
- 設計「前後只允許這些差異」型閘門：預期差異從檢查器程式碼推（grep 哪些檢查讀到被改的屬性，逐項列預期），不憑印象列。

**另外兩條**：
- 修完審查 finding 後：反查全文有沒有其他段落引用被改的數值或結論，一併更新再送複驗。
- 判定策略「無效／負向」：必附具名的真實失敗案例（哪筆交易、進場日、報酬、失敗機制），不能只給平均值。

正例：採用新版時附受控對照、其餘訊號 bit-identical、時間前後半各自驗證。
反例：只看單一訊號 PF 上升就宣告改良成功（合池 PF 才是真實評估）。

## Rubric 3：何時停下來問使用者

**必問（任一）**：
- 動作不可逆或影響超出任務範圍：刪檔、改 DB schema、動 production 的 .bat／NSSM 服務、git 破壞性操作、對外發送（用正式 bot token 發到任何 chat 都算）
- 不確定的套件選擇、架構方向、實作方式
- 搜尋或嘗試 3 次未果
- 規格有 ≥2 種合理解讀，且選錯會浪費 >30 分鐘
- 發現任務前提可能錯了（要改的東西已被別的機制取代、需求與既有設計衝突）
- harness 預設與專案規則衝突，而 CLAUDE.md 沒寫誰優先：不猜，當場問，並把裁定寫回制度檔

**不必問（自己決定、記下理由、繼續）**：可逆、在範圍內、不影響最終結果的順序／命名／風格選擇。「不必問」只表示這類分支不進 Grill-Me 逼問樹；CLAUDE.md Grill-Me 第 5 步的空樹阻塞確認仍要做。

正例：殺 Python process 前先確認 parent（這台機器上有別的工具會被 cmdline 誤中）。
反例：「變數叫什麼」「先寫測試還是先寫實作」——問了只是把決策成本轉嫁給使用者。

## Rubric 4：方向錯了該換路（不是重試）的訊號

**任一命中 → 停止此路，換方法或回報**：
- **命中失敗封存**：提案對上 MEMORY.md 標「勿重試／別重提／MUST NOT／已驗證不採用」的條目 → 直接停，回報「此方向已封存於 `<memory 檔名>`」。使用者明示重開才做。
  - 回測任何訊號／防守參數前，先讀該子專案 memory **檔案全文**，不能只看 MEMORY.md 的索引行（索引行塞不下具體參數結論）。
- **同一方向連 3 個變體都負向** → 前提錯了，不是參數沒調好。（這是「結果負向」的計數；[01_dispatch.md](01_dispatch.md) §5 的「執行失敗最多重試 2 輪」是另一個計數，不要混。）
- **打地鼠**：每修一個問題冒出一個新問題 → 錯的是架構層。
- **例外條款越加越多**才能讓方案成立。
- **審查不收斂**：同一份設計或控制機制連 2 輪審查都「修一個、冒一個」→ 停止逐條補，改寫成單一狀態表（狀態、轉換、共用判定式）再送審。改寫後下一輪仍有高嚴重度問題，或安全／完整性控制連 3 輪都有新的高嚴重度項目 → 停，不再出新版；回報使用者並建議重估範圍（列出可延後或拿掉的部分），或先寫出威脅模型與要保證的性質。
- **症狀是「使用者沒看到 X」** → 先分三層各自驗：模型有沒有產生、harness 有沒有傳、介面有沒有顯示。不可只改 prompt。

正例（早該換路）：同一個構想連做 11 版全負才收手，第 3 版全負時就該質疑前提。
反例（不該換路）：第一次跑就報錯——先讀錯誤訊息、修一次再說。

## Rubric 5：回測改動的採用底線 ★

**觸發**：要採用任何訊號／評分／攻防改動。**全部通過**才採用（流程照 skill `signal-factory`）：

1. 合池 PF 上升，不只單訊號
2. 時間均勻：前半、後半期各自為正；增益集中單一事件（2020 崩盤是慣犯）＝不採用
3. 三大目標零違反（勝率、最大虧損、交易質量）；交易數↑但 PF 不升＝負向
4. 採用參數落在 plateau 上而非孤峰；sweep 曲線單調時必須加查時間分布
5. 未改動的訊號結果 bit-identical
6. 證據品質：引用表格的任何一格前先看那格的 n；從別處借來的參數要在本序列重掃；評分系統要跑逐年拆解；攻防／曝險型用每單位曝險年化，並先數差異日（<20 天或集中單一年不採用）；單口系統的進場濾網要比對「被擋交易損益總和」

## Rubric 6：背景工作與長指令的完成判定

**觸發**：派背景 agent、用 `run_in_background`、等任何長指令。

- `run_in_background` 的指令**直接寫本體**，不可再套 `&`／`nohup`／`Start-Process`（雙重背景會立刻發出假的完成通知）。
- 完成與否看**產出檔實況**（mtime、大小、內容），不看 log 的中間字樣，不等 agent 自己回報。
- agent 回報「已派出／執行中／等通知」＝空回報，不是進度：用 `SendMessage` 糾正一次（「你自己就是執行者，立即親自執行原 prompt」），不要急著重派。
- 預期 >10 分鐘的指令不要掛 tool timeout。

正例：build 完成通知來了，仍去查 exe 的 mtime 確認真的被覆寫。
反例：看到 log 出現「completed successfully」字樣就宣告完成（那是中間步驟）。

## Rubric 7：驗收對象要在生產路徑上

**觸發**：驗收任何改動、宣告「已修好」。

- 實跑輸出只證明「這段程式碼會這樣算」。驗收前先確認被改的函式**在生產呼叫鏈上**（從服務／排程／bot 指令往下追到它）。
- 本 repo 的門檻常是多份寫死的複製：改門檻要搜**數值字面**（如 `100, 25, 500`），不搜函式名。
- 餵給驗收 agent 的中介檔（dump、轉檔、摘要）要與被驗物在同一個指令內重建，或讓 agent 直接讀原始檔。

正例：改完離線報表的門檻後，搜數值字面，發現 bot 即時版另有三份複製，一併改。
反例：改了只有 CLI 用的檔並實跑通過，就回報使用者「誤報已修」——bot 走的是另一個檔。

## Rubric 8：受控比對的分母必須自己閉合 ★

**觸發**：任何 A/B 比對、批次重跑、稽核腳本、完整性檢查。驗收時逐條斷言，不以「腳本正常結束」代替：

1. 印出來的母體數 == 結果紀錄筆數 == 各 outcome 之和＋`measurement_error` 數＋非受測 producer 的列數
2. 每個嘗試過的樣本恰好一筆結果紀錄；沒有結果＝沒測到，不是沒事
3. 下載失敗、逾時等 `measurement_error` 不算成效，但仍是一筆紀錄
4. 失敗路徑不可 `continue` 掉紀錄：**失敗本身要產生紀錄**
5. 不用寬鬆的存在性條件冒充完整性（「當日有列」「筆數 >0」）；用與參考欄位的比例，並按市場別分開統計
6. 腳本的聚合 key 不得比要主張的單位粗（主張每家公司 → key 至少是公司）
7. 比對前先驗比對函式自己：兩臂序列化路徑不同要先正規化，並用一組已知 unchanged 的樣本試跑

## Rubric 9：結構化原始碼不以裸字串替換編輯 ★

**觸發**：用「找一段文字換成另一段」的方式改 `.py`／`.sql`／`.json`。

- anchor 必須唯一：`assert count == 1`，不等於 1 **就不寫入**
- anchor 用結構終止符，不用段落中段的文字；不以「從某定義切到下一個通用標記」為範圍
- 寫入後驗**結構**：`.py` 用 `ast.parse` 或 import；`.json` 用 `json.loads`；`.sql` 不在正式資料庫驗語法
- 含跳脫序列的內容用檔案寫入，不用 shell heredoc；寫完用讀 bytes 計數驗，不用目視
- 自問：「我這次替換的範圍，有沒有包含我沒打算動的東西？」（測試全綠不足以證明）

## Rubric 10：寫入權是一份合約 ★

**觸發**：任何有持久效果的動作（DB 寫入、分類變更、commit、推 main、排程狀態、**寫出 migration 檔**），或稽核過去的這類動作。寫入前四軸都要答得出來：

| 軸 | 問自己 |
|---|---|
| 範圍 | 實際要做的每一筆變更，都落在授權的**文字**範圍內嗎？ |
| 授權 | 使用者同意的是「對象集合」，還是連「內容」也看過？ |
| 條件 | 授權附帶的前提、覆核、驗收、順序，都在寫入前履行並取得確認了嗎？ |
| 執行 | 實際寫入的內容和裁定文字一致嗎？ |

- 「繼續／好」不等於批次授權。前一則訊息只列了要處理哪些東西、沒列要寫成什麼 → 先把內容給使用者看。
- 條件是授權的一部分：說過「列給你覆核」「先出草案」，就要先交付、得到回應才寫入。事後沉默不算履行。
- **順序被使用者鎖定時**：前一步含還沒回報的背景複核 → 等它回報並處理完才做下一步，即使下一步看似獨立。等待期間只做不屬於後續步驟的事。
- **界線照字面執行**：寫「不得連線」→ 連線本身就被禁止，與查詢是否唯讀無關。唯讀任務的操作清單要分開列「允許連線的對象」與「允許的 SQL」。
- 範圍外的變更先停下來另取授權，不能用「結果合理」補正。
- 寫出 migration 檔＝排定正式 DB 寫入（`init_db()` 會自動套用）；要在 session 內套用就呼叫 `init_db()`，不直接 execute 檔案內容。
- 建新裁定前先查既有裁定紀錄（裁定檔、ledger）：DB 上「已裁定未寫入」和「從未裁過」長得一樣。

## Rubric 11：跑任何可能寫入共用狀態的指令前 ★

**觸發**：要跑的腳本或測試可能寫入 DB、共用產出檔、production 資料。「只是測試」不改變它寫到哪裡。

- 先讀腳本的進入點與參數解析，確認旗標真的被解析（未被解析的旗標＝直接執行本體）。不用 memory 或文件的描述代替讀檔。
- 會寫共用產出路徑的腳本，執行前先備份該產出檔。
- 破壞性對照測試不靠 `finally: rollback` 收尾：先確認連線不會 commit 到正式狀態，測完查殘留。
- 會 append 紀錄的腳本，重跑不得產生重複紀錄。
- **多階段寫入（改檔 → seed → 驗收）**：每一階先驗後寫（寫暫存檔、驗過才 `os.replace`）；階段之間用 exit code 閘門（`if [ $rc -eq 0 ]`），不用 `;` 串接。

## Rubric 12：效能與時長估計的基準要實測

**觸發**：提「省下 N 次 × 每次 T」型提案，或估計長批次的時長。

- 單位成本用實測值，不用直覺或參數設定值推算。
- 牆鐘時間依該路徑的實際並行度估；序列路徑與並行路徑的效益分開列。
- 時間報告用具名欄位 `wall_clock_hours` 與 `sum_of_batch_minutes`，不用「已耗」；進行中批次已跑的時間不重複計入前瞻估計。

正例：提連線池前先量單次握手（16ms），發現並行路徑牆鐘只省 2%。
反例：用 pace 參數（20 秒／家）估批次時長，漏算下載與解析，估 7.6h 實際 10.5h。

## 誠實條款

拆解、驗證、多樣本評審補得了**執行品質**；**模糊題與品味判斷**補不了。遇到品味題（該不該採用、兩個都對選哪個、命名／文案）依序：

1. 派 fresh-context 對抗審查，prompt 附正反雙方論據
2. 仍拿不準 → 生成 2–3 個獨立答案，派 fresh agent 評審選優
3. 仍分歧 → 明說「這題超出我能可靠判斷的範圍」，附選項與 tradeoff 給使用者裁決

禁止假裝有把握。在這個專案，一個錯誤的採用會污染之後所有版本的 baseline。遇到沒有任何 Rubric 覆蓋的情境：用自己的判斷並說出理由，不要硬套一條；判斷不了才走第 3 步。
