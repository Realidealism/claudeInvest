# 02 判斷力 Rubrics

把「什麼時候該做什麼」寫成可執行判準。每條附本專案真實正反例（完整脈絡在 memory/ 對應檔案，例子後括號註明）。

## Rubric 1：何時升級模型 / 找第二意見

**升級訊號（任一命中即升，配合 [01_dispatch.md](01_dispatch.md) §5）**：
- 問題本質是「取捨」而非「執行」：多個方案各有利弊、或驗收標準本身需要先被定義
- 數字都算對了，但「該不該採用」拿不準（統計顯著 vs 過擬合、增益來源乾不乾淨）
- 同一子任務失敗 2 次，且兩次失敗原因**不同**（原因相同是執行問題，修就好；原因不同代表理解錯了）

**正例**：v351 的門檻掃描結果單調遞增，機械上看該採用最緊值；但增益全來自 2020 崩盤的深空贏單——「sweep 單調 ≠ 可採用，必須時間均勻」是品味判斷，這種問題該派 opus 第二意見而不是自己拍板（project_v351_baseline）。
**反例（不該升級）**：把已驗證的 give-back 條件複製到另一個訊號並跑回測——純執行，sonnet 足夠；升級只是變慢變貴。

## Rubric 2：何時算「真的完成」

完成 = **驗收證據在手**，不是「我改完了」：
- 程式碼：測試綠 / 實跑輸出貼在回報裡。回測改動：六訊號全跑完 + sanity（未動的訊號結果 bit-identical）
- 檔案/文件：fresh agent read-back 通過（[01_dispatch.md](01_dispatch.md) §6）
- 修 bug：能說出**根因**並解釋舊行為為何發生。「改了之後不再出現」不算——可能只是壓住症狀
- 涉及排程/服務（.bat、NSSM、cron）：實際觸發一次或查到下次排程時間，不能只看檔案內容對
- **判定策略「無效益/負向」**：MUST 附**實際失敗的真實案例**（具名交易/受害股 + 進場日 + 報酬 + 失敗機制），不能只給 aggregate（PF/勝率/均值）。理由：均值藏假象——2026-07 判「無 edge」時，是列受害股才發現「-92.7% 崩塌」實為世紀分割的資料假象，改寫了結論。負向結論跟正向採用一樣要交待證據（signal-factory §1a 受害股同精神，延伸到所有策略分析）。

**正例**：v352 採用時附受控對照（同資料、僅 pick+sell_flee 變）＋其餘 4 訊號 bit-identical＋時間前後半雙驗證＋sweep plateau 確認非 overfit（project_v352_baseline）。
**反例**：只看單一訊號 PF 上升就宣告改良成功。合池 PF 才是真實評估，單訊號 PF 升可能是把爛單推給別的訊號（feedback_signal_portfolio_eval）。

## Rubric 3：何時停下來問使用者

**必問（任一命中）**：
- 動作不可逆或影響超出任務範圍：刪檔、改 DB schema、動 production .bat/NSSM 服務、git 破壞性操作、對外發送
- 不確定的套件選擇、架構方向、實作方式（CLAUDE.md 既有規則——這類選錯通常代價高或難回頭）
- 搜尋/嘗試 3 次未果（CLAUDE.md 既有規則）
- 規格有 ≥2 種合理解讀，且選錯會浪費 >30 分鐘的工作
- 發現任務前提可能錯了（要改的東西看起來已被別的機制取代、或需求與既有設計衝突）

**不必問（自己決定、記下理由、繼續）**：可逆、在範圍內、對最終結果無影響的順序/命名/風格類選擇——這類不屬於 CLAUDE.md 說的「技術決策」。

**正例**：殺 Python process 前先確認 parent——使用者機器上有其他 telegram bot 工具會被 cmdline 誤中，環境事實拿不準就問（feedback_process_kill_safety）。
**反例**：「變數名用哪個」「先寫測試還是先寫實作」（結果相同，只是順序）——問了只是把決策成本轉嫁給使用者，這種自己決定。

## Rubric 4：方向錯了該換路（不是重試）的訊號

**任一命中 → 停止此路，換方法或回報**：
- 提案命中 MEMORY.md 的失敗封存條目（標「勿重試/別重提/MUST NOT/已驗證不採用」）→ **直接停**，回報「此方向已封存於 `<memory 檔名>`」；除非使用者明示重開
- 同一方向連 3 個變體都負向 → 前提錯了，不是參數沒調好（此為「變體結果負向」的計數軸，與 [01_dispatch.md](01_dispatch.md) §5「同一做法**執行失敗**最多重試 2 輪」是不同計數，勿混）
- 打地鼠：每修一個問題冒出一個新問題 → 錯的是架構層不是當前 bug
- 為了讓方案成立，例外條款越加越多（if 特殊情況 A 就跳過、B 再跳過…）

**正例（早該換路）**：momentum_override 連做 11 版（v309–v319）全負才收手。第 3 版全負時就該質疑前提（portfolio dilution 天花板），後 8 版是浪費（project_momentum_override_failed）。
**正例（封存即停）**：flee force-exit 復活已標 MUST NOT——結構性死路（緊 trailing 永遠早於反轉訊號觸發），再聰明的變體都不要試（project_flee_force_exit_revival_failed）。
**反例（不該換路）**：第一次跑就報錯——先讀錯誤訊息、修一次再說。單次失敗不構成換路理由。

## Rubric 5：品質底線怎麼驗（回測改動特化）

採用任何訊號改動前，**全部通過**才算（詳細流程照 skill `signal-factory`，此處是底線清單）：
1. 合池 PF 上升，不只單訊號
2. 時間均勻：前半/後半期各自為正；增益集中在單一事件（2020 崩盤是慣犯）= overfit，不採用
3. 三大目標零違反：勝率、maxL（最大虧損）、交易質量；交易數↑但 PF 不升 = 負向
4. sweep robustness：採用參數落在 plateau 上而非孤峰；掃描曲線單調時**必須**加查時間分布（見 Rubric 1 正例）
5. sanity：未改動的訊號結果 bit-identical

## 誠實條款

拆解、驗證、多樣本評審補得了**執行品質**；**模糊題與品味判斷**補不了。遇到品味題（該不該採用、兩個都對選哪個、命名/文案/美感）依序：
1. 派 `opus` 第二意見，prompt 附正反雙方論據
2. 仍拿不準 → 生成 2–3 個獨立答案，派 fresh agent 評審選優
3. 仍分歧 → 明說「這題超出我能可靠判斷的範圍」，附選項與 tradeoff 給使用者裁決

禁止假裝有把握。錯誤的自信比「我不確定」貴得多——尤其在這個專案，一個錯誤採用會污染之後所有版本的 baseline。
